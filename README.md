# libretro-ios-lab

A spike repo for building [libretro](https://www.libretro.com/) cores for Apple platforms and
driving them from Swift — verified end to end on **GitHub-hosted macOS CI**.

## Why this exists

The app this feeds into runs NES/SNES/etc. inside an iOS Tauri shell using an in-process
libretro core (`tauri-plugin-libretro`) instead of a WebView emulator. Getting that green was
blocked by two things at once:

* the private repo's iOS workflow had been moved to a **self-hosted** macOS runner that is not
  currently registered, so no build can start at all;
* macOS minutes bill at ~10× Linux on private repos, which is what forced the move.

GitHub-hosted runner usage on **public** repositories is free and unmetered, and stays free
after the March 2026 pricing change. So the risky, iterative parts — cross-compiling the core,
getting the slices into one xcframework, proving the Swift host actually drives it — get
worked out here, on hosted runners, with a real test suite. The validated recipe then goes
back into the app repo as the e2e.

## What is actually being tested

`Sources/CLibretro/**` and `Sources/LibretroKit/LibretroHost.swift` are **byte-for-byte copies
of the shipping plugin's files**. `LibretroHost.swift` imports only `CLibretro`, `Foundation`
and `QuartzCore` — no Tauri — which is what makes this possible. `Package.swift` is the
plugin's manifest minus the Tauri dependency. So a green run here is evidence about the real
code, not about a lookalike.

CI runs three tiers on one runner:

| Tier | What it proves |
| --- | --- |
| `swift test` on macOS arm64 | The host links against the core and the core *runs* — fastest signal. |
| `xcodebuild test` on the iOS Simulator | The same tests pass on an iOS slice. |
| `xcodebuild build` for `generic/platform=iOS` | The iOS **device** slice links (can't be run on CI, but catches missing symbols before TestFlight). |

## The two findings this repo is built around

**1. `platform=osx CROSS_COMPILE=1` beats `platform=ios-arm64`.**
fceumm's `Makefile.libretro` has, inside the `osx` branch:

```make
ifeq ($(CROSS_COMPILE),1)
    TARGET_RULE = -target $(LIBRETRO_APPLE_PLATFORM) -isysroot $(LIBRETRO_APPLE_ISYSROOT)
    CFLAGS  += $(TARGET_RULE)
    LDFLAGS += $(TARGET_RULE)
endif
```

One recipe, any Apple slice — macOS, iOS device, and crucially **iOS Simulator**. The
`ios-arm64` branch hardcodes `cc -arch arm64 -isysroot $(IOSSDK)` and offers no simulator
target; `-arch` alone also doesn't stamp a distinct `LC_BUILD_VERSION`, which is what makes
`xcodebuild -create-xcframework` reject device and simulator slices as duplicates.

**2. Do not set `STATIC_LINKING=1`.**
`Makefile.common` wraps the bundled libretro-common sources in `ifneq ($(STATIC_LINKING),1)`,
assuming a RetroArch frontend supplies `filestream_*` / `path_is_valid` /
`fill_pathname_join`. A Swift host does not, so the flag yields undefined symbols at the final
link. `tools/build-core.sh` asserts `_filestream_open` is present precisely to catch a
regression here.

## The test ROM

`Tests/LibretroKitTests/Resources/testrom.nes` is generated by `tools/make-test-rom.mjs` and is
our own work (public domain) — no commercial ROMs live here. It is a minimal NROM image that:

* sets the universal backdrop `$3F00` to a bright blue and turns on background rendering, so
  **every** pixel is that colour regardless of what garbage the emulator powers VRAM up with
  (colour index 0 of every palette mirrors the backdrop). A black frame therefore can only
  mean the core never ran;
* starts a constant-volume square wave with the length counter halted, so silence is also a
  real failure.

CI regenerates it and `cmp`s against the committed copy, so the two can't drift.

## Local use

```sh
./tools/build-core.sh     # clones fceumm, builds 3 slices, writes fceumm.xcframework
swift test
```

`fceumm.xcframework` is git-ignored and must exist before any `swift`/`xcodebuild` command —
`Package.swift` declares it as a binary target, so resolution fails without it.
